# 01 环境与部署设计

> 文档状态：初稿，待项目负责人确认（2026-11-16）。
> 上位文档：`docs/00-总体架构设计.md` 第 5 节与第 10 节。对应里程碑：M0。
> 本文档中标注“待验证”的内容是架构师无法事先确定的事项，由对应的任务卡在实现过程中验证并反馈。

## 1. 设计目标与范围

里程碑 M0 的目标是在一台阿里云服务器上，用 Docker Compose 启动核心组、实时组、调度组和治理组四个分组，并且通过两条冒烟测试证明离线链路与实时链路的基础设施可用。

本文档的范围不包括平台组。平台组的两个容器依赖尚未开发的 Web 平台代码，它们的编排放在里程碑 M6 中完成。本文档也不包括任何业务表、业务作业和调度工作流。

## 2. 服务器与目录约定

| 项目 | 约定 |
| --- | --- |
| 服务器规格 | 阿里云 ECS，x86 架构，8 核 CPU，32 GB 内存，200 GB 云盘。 |
| 操作系统 | Ubuntu 22.04。 |
| 容器运行时 | Docker Engine 与 Docker Compose 插件，使用 `docker compose` 命令。 |
| 仓库位置 | `/opt/dataplatform`，全部环境类脚本以该目录为工作目录。 |
| 时区 | 全部容器统一设置为 `Asia/Shanghai`。 |
| 数据持久化 | 全部有状态容器使用 Docker 命名卷，卷名以 `dp_` 开头。 |

仓库中与部署有关的文件全部位于 `deploy/` 目录，结构如下：

```
deploy/
├── docker-compose.yml        全部分组的编排文件，以 profile 区分分组
├── .env.example              环境变量模板，包含镜像名称、版本号和默认密码
├── images/                   自建镜像的构建目录
│   ├── hadoop-base/          JDK 8 与 Hadoop 3.3.6，HDFS 与 YARN 容器共用
│   ├── hive/                 在 hadoop-base 之上增加 Hive 3.1.3
│   ├── gateway/              在 hive 之上增加 Spark 与 Flink 客户端
│   └── dolphinscheduler/     在官方镜像之上增加 Hadoop 与 Spark 客户端
├── conf/                     各组件的配置文件，按组件名分目录，以只读方式挂载到容器
├── init/                     初始化脚本，例如 MySQL 建库脚本
└── scripts/                  启动、停止、健康检查与冒烟测试脚本
```

## 3. 镜像策略

镜像分为自建镜像与官方镜像两类。

| 镜像 | 类型 | 基础 | 自建的原因 |
| --- | --- | --- | --- |
| `dp-hadoop-base` | 自建 | JDK 8 的官方基础镜像，加上 Hadoop 3.3.6 的发行包 | 保证 HDFS、YARN、Hive 与 Spark 客户端使用同一套 JDK 8 和 Hadoop 版本。 |
| `dp-hive` | 自建 | `dp-hadoop-base`，加上 Hive 3.1.3 的发行包 | 需要替换 Guava 依赖包，并放入 MySQL 驱动。 |
| `dp-gateway` | 自建 | `dp-hive`，加上 Spark 3.5.x 与 Flink 1.20.x 的发行包 | 作为统一的作业提交入口，需要同时具备三种客户端。 |
| `dp-dolphinscheduler` | 自建 | DolphinScheduler 3.4.2 的官方单机镜像 | 调度节点需要能够执行 `spark-submit` 与 `hdfs` 命令。 |
| MySQL、Kafka、Flink、ClickHouse、DataHub、OpenSearch | 官方 | 各项目发布的官方镜像 | 不需要定制。 |

镜像策略遵循以下四条规则：

1. 全部镜像的名称与标签都在 `.env.example` 中以变量声明，编排文件只引用变量。这样做有两个目的：一是把版本号固定在一处，二是在服务器无法访问 Docker Hub 时，可以把变量改为阿里云容器镜像服务中的地址，而不需要修改编排文件。
2. 标签必须固定到具体的版本号，不得使用 `latest`。本文档只规定了主版本与次版本的组件，由任务卡的实现者选定当时最新的修订版本，并在合并请求中说明。
3. 自建镜像在服务器上通过 `docker compose build` 构建。Hadoop、Hive、Spark 与 Flink 发行包的下载地址以构建参数的形式声明，默认值为 Apache 官方归档站点，可以在 `.env` 中改为国内镜像站点。
4. 发行包在构建镜像时下载，不得提交到仓库。

## 4. 分组与容器

四个分组对应 Docker Compose 的四个 profile，名称分别为 `core`、`realtime`、`scheduler` 和 `governance`。全部容器加入同一个名为 `dp-net` 的网络，容器之间以服务名互相访问。

| 分组 | 服务名 | 镜像 | 职责 |
| --- | --- | --- | --- |
| core | `mysql` | MySQL 8.0 | 承载模拟业务库、Hive Metastore 库、调度库、DataHub 库和平台库。 |
| core | `namenode` | `dp-hadoop-base` | HDFS 的名称节点。 |
| core | `datanode` | `dp-hadoop-base` | HDFS 的数据节点，副本数为 1。 |
| core | `resourcemanager` | `dp-hadoop-base` | YARN 的资源管理器。 |
| core | `nodemanager` | `dp-hadoop-base` | YARN 的节点管理器，Spark 作业在其中运行。 |
| core | `hive-metastore` | `dp-hive` | Hive 元数据服务。 |
| core | `hiveserver2` | `dp-hive` | 交互式查询入口，只用于查询与验证，不承担 ETL。 |
| core | `gateway` | `dp-gateway` | 作业提交网关，常驻运行，人工与脚本都通过它提交 Spark 与 Flink 作业。 |
| realtime | `kafka` | Kafka 3.9.x | 单节点，KRaft 模式。 |
| realtime | `flink-jobmanager` | Flink 1.20.x（Java 8 标签） | Flink 独立集群的作业管理器。 |
| realtime | `flink-taskmanager` | Flink 1.20.x（Java 8 标签） | Flink 独立集群的任务管理器，提供 4 个任务槽。 |
| realtime | `clickhouse` | ClickHouse 长期支持版本 | 服务层存储。 |
| scheduler | `dolphinscheduler` | `dp-dolphinscheduler` | 单机模式的调度服务，元数据存放在 MySQL 中。 |
| governance | `opensearch` | OpenSearch | DataHub 的检索引擎。 |
| governance | `datahub-gms` | DataHub 1.7.0 | DataHub 的元数据服务。 |
| governance | `datahub-frontend` | DataHub 1.7.0 | DataHub 的前端。 |
| governance | `datahub-actions` | DataHub 1.7.0 | DataHub 的动作服务，用于执行界面上配置的采集任务。 |

分组之间存在以下依赖关系，启动脚本必须按照依赖顺序启动：

- `realtime` 分组中的 Flink 需要访问 `core` 分组的 MySQL 与 HDFS，因此启动 `realtime` 之前必须先启动 `core`。
- `scheduler` 分组依赖 `core` 分组的 MySQL、HDFS 与 YARN。
- `governance` 分组依赖 `core` 分组的 MySQL 和 `realtime` 分组的 Kafka。

Flink 采用独立集群而不是运行在 YARN 上。这样做的理由是实时作业需要常驻运行，独立集群使它与离线作业的 YARN 资源互不争抢，部署也更简单。

## 5. 内存上限

每个容器都必须在编排文件中设置内存上限，JVM 类组件还必须把堆内存设置为明显小于容器上限的数值。下表中的数值是初始设定，由 M0 的各张任务卡实测之后在合并请求中反馈实际占用，架构师据此修订。

| 分组 | 服务名 | 容器内存上限 | 关键内存参数 |
| --- | --- | --- | --- |
| core | `mysql` | 1 GB | 无。 |
| core | `namenode` | 1 GB | 堆内存 512 MB。 |
| core | `datanode` | 1 GB | 堆内存 512 MB。 |
| core | `resourcemanager` | 1 GB | 堆内存 512 MB。 |
| core | `nodemanager` | 5 GB | `yarn.nodemanager.resource.memory-mb` 为 4096，`yarn.nodemanager.resource.cpu-vcores` 为 4，关闭虚拟内存检查。 |
| core | `hive-metastore` | 1 GB | 堆内存 512 MB。 |
| core | `hiveserver2` | 1.5 GB | 堆内存 1 GB。 |
| core | `gateway` | 1 GB | Spark 作业一律以 cluster 模式提交，驱动程序不在网关中运行。 |
| realtime | `kafka` | 1.5 GB | 堆内存 1 GB。 |
| realtime | `flink-jobmanager` | 1 GB | `jobmanager.memory.process.size` 为 900m。 |
| realtime | `flink-taskmanager` | 2 GB | `taskmanager.memory.process.size` 为 1800m，`taskmanager.numberOfTaskSlots` 为 4。 |
| realtime | `clickhouse` | 2 GB | 服务端内存使用比例上限设置为 0.8。 |
| scheduler | `dolphinscheduler` | 2 GB | 堆内存 1 GB。 |
| governance | `opensearch` | 2 GB | 堆内存 1 GB。 |
| governance | `datahub-gms` | 2 GB | 堆内存 1 GB。 |
| governance | `datahub-frontend` | 1 GB | 堆内存 512 MB。 |
| governance | `datahub-actions` | 512 MB | 无。 |

四个分组的内存上限合计为 26.5 GB，其中 core 为 12.5 GB，realtime 为 6.5 GB，scheduler 为 2 GB，governance 为 5.5 GB。加上里程碑 M6 中平台组的 1.25 GB，总计约 28 GB，服务器保留约 4 GB 给操作系统。

YARN 可用内存为 4096 MB，据此约定 Spark 作业的默认资源为：驱动程序 1 GB，执行器 2 个，每个执行器 1 GB 内存和 1 个核。同一时间只运行一个 Spark 作业。

## 6. 端口与访问方式

原型中的 HDFS、YARN、Kafka 等组件没有启用身份认证，因此全部端口只允许绑定到服务器的 `127.0.0.1`，不得绑定到 `0.0.0.0`。阿里云安全组只开放 SSH 端口，项目负责人通过 SSH 隧道访问各管理页面。

| 服务名 | 容器端口 | 映射到服务器的端口 | 用途 |
| --- | --- | --- | --- |
| `mysql` | 3306 | 3306 | 数据库连接。 |
| `namenode` | 9870 | 9870 | HDFS 管理页面。容器之间通过 8020 端口访问文件系统，该端口不映射。 |
| `resourcemanager` | 8088 | 8088 | YARN 管理页面。 |
| `hiveserver2` | 10000、10002 | 10000、10002 | JDBC 连接与管理页面。 |
| `kafka` | 9092、19092 | 19092 | 容器之间使用 9092 端口，服务器本机使用 19092 端口。 |
| `flink-jobmanager` | 8081 | 8081 | Flink 管理页面。 |
| `clickhouse` | 8123、9000 | 8123、9000 | HTTP 接口与原生协议接口。 |
| `dolphinscheduler` | 12345 | 12345 | 调度管理页面。 |
| `datahub-frontend` | 9002 | 9002 | DataHub 页面。 |
| `datahub-gms` | 8080 | 8080 | DataHub 接口，供血缘上报与质量结果上报使用。 |
| `opensearch` | 9200 | 不映射 | 只供 DataHub 在容器网络内访问。 |

端口 8090 与 8000 预留给里程碑 M6 中的平台后端与平台前端。

通过 SSH 隧道访问管理页面的方式如下：

- **执行环境**：项目负责人的本地电脑，任意目录。
- **调用命令**：`ssh -N -L 9870:127.0.0.1:9870 -L 8088:127.0.0.1:8088 -L 8081:127.0.0.1:8081 -L 12345:127.0.0.1:12345 -L 9002:127.0.0.1:9002 <用户名>@<服务器公网地址>`
- **前置条件**：服务器上对应的分组已经启动，本地电脑的这些端口没有被占用。
- **期望产出**：命令保持运行期间，在本地浏览器访问 `http://127.0.0.1:9870` 等地址可以打开对应的管理页面。
- **常见失败兜底**：提示端口已被占用时，把 `-L` 参数中冒号之前的本地端口改为其他数值。页面无法打开时，先在服务器上执行健康检查脚本确认容器正常。

## 7. 关键配置

### 7.1 MySQL

MySQL 首次启动时由 `deploy/init/` 中的脚本创建下表中的数据库与账号，密码全部来自 `.env` 文件。

| 数据库 | 用途 | 账号 |
| --- | --- | --- |
| `mes`、`qms`、`erp` | 模拟业务库，在里程碑 M1 中建表。 | `dp_source` |
| `hive_metastore` | Hive 元数据。 | `hive` |
| `dolphinscheduler` | 调度元数据。 | `dolphinscheduler` |
| `datahub` | DataHub 元数据。 | `datahub` |
| `dp_portal` | Web 平台的业务数据，在里程碑 M5 与 M6 中建表。 | `dp_portal` |

MySQL 的二进制日志必须保持开启并采用 ROW 格式，字符集为 `utf8mb4`。另外创建一个只用于变更捕获的账号 `dp_cdc`，授予读取 `mes` 与 `qms` 以及复制所需的权限。

### 7.2 HDFS 与 YARN

- `fs.defaultFS` 的值为 `hdfs://namenode:8020`，副本数为 1，关闭 HDFS 权限检查。
- YARN 使用容量调度器的默认队列，日志聚合保持开启，以便通过 `yarn logs` 命令查看作业日志。
- 全部 Hadoop 进程以同一个系统用户运行，避免目录权限问题。

### 7.3 Hive

- Hive 3.1.3 自带的 Guava 依赖包版本低于 Hadoop 3.3.6 所需的版本，构建 `dp-hive` 镜像时必须用 Hadoop 自带的 Guava 依赖包替换它。
- Hive Metastore 使用 MySQL 作为元数据库，首次启动时通过 `schematool` 初始化元数据表，重复启动时不得重复初始化。
- 数据仓库目录为 `/user/hive/warehouse`。
- HiveServer2 关闭用户身份模拟，并且不启用认证。

### 7.4 Spark

- Spark 只以客户端的形式存在于 `gateway` 容器中，不部署独立的 Spark 集群，作业通过 `--master yarn --deploy-mode cluster` 提交。
- Spark 3.5 内置的 Hive 客户端版本为 2.3.9，因此必须在 `spark-defaults.conf` 中把 `spark.sql.hive.metastore.version` 设置为 `3.1.3`，并且把 `spark.sql.hive.metastore.jars` 指向镜像中的 Hive 3.1.3 依赖包目录。
- `spark.sql.catalogImplementation` 设置为 `hive`，Spark 创建的表与 HiveServer2 看到的表必须一致。

### 7.5 Kafka、Flink 与 ClickHouse

- Kafka 配置两个监听器：容器网络内的客户端使用 `kafka:9092`，服务器本机的客户端使用 `127.0.0.1:19092`。自动创建主题的功能保持关闭，主题由脚本显式创建。
- Flink 的检查点目录为 `hdfs://namenode:8020/flink/checkpoints`，因此 Flink 镜像需要能够访问 HDFS。实现方式待验证：优先通过挂载 Hadoop 配置并设置 `HADOOP_CLASSPATH` 实现。
- Flink 作业所需的连接器依赖包由各作业自行打包，不放入 Flink 的 `lib` 目录。冒烟测试所需的连接器除外。
- ClickHouse 创建一个名为 `dp` 的数据库和一个名为 `dp` 的账号。

### 7.6 DolphinScheduler 与 DataHub

- DolphinScheduler 采用单机模式，元数据库改为 MySQL，因此镜像中需要放入 MySQL 驱动。
- DolphinScheduler 的容器内需要具备 `hdfs` 与 `spark-submit` 命令以及对应的配置文件，使 Shell 任务与 Spark 任务能够向 YARN 提交作业。
- DataHub 的编排以其 1.7.0 版本官方发布的编排文件为基础裁剪，去掉其中自带的 MySQL 与 Kafka，改为连接本项目的 `mysql` 与 `kafka`。
- DataHub 复用外部 Kafka 时不再单独部署模式注册中心。实现方式待验证：优先使用元数据服务内置的模式注册功能。

## 8. 脚本约定

`deploy/scripts/` 目录下提供以下五个脚本。每个脚本的头部注释必须按照 `AGENTS.md` 第 12 节的要求说明五项内容，并且在失败时以非零退出码结束。

| 脚本 | 调用方式 | 行为 |
| --- | --- | --- |
| `dp-up.sh` | `bash deploy/scripts/dp-up.sh <分组名> [分组名...]` | 按照依赖顺序启动指定的分组，并等待容器进入健康状态。 |
| `dp-down.sh` | `bash deploy/scripts/dp-down.sh <分组名> [分组名...]` | 停止指定的分组，保留数据卷。 |
| `dp-health.sh` | `bash deploy/scripts/dp-health.sh <分组名>` | 逐项检查指定分组的每个服务，输出每一项的结果。全部通过时退出码为 0。 |
| `smoke-offline.sh` | `bash deploy/scripts/smoke-offline.sh` | 执行离线冒烟测试，见第 9.1 节。 |
| `smoke-realtime.sh` | `bash deploy/scripts/smoke-realtime.sh` | 执行实时冒烟测试，见第 9.2 节。 |

健康检查必须检查服务的实际可用性，而不只是检查容器是否在运行。例如，HDFS 的检查项是能够列出根目录，YARN 的检查项是存在一个处于运行状态的节点，Hive 的检查项是能够通过 JDBC 执行 `show databases`。

删除数据卷属于破坏性操作，不提供脚本，需要时由项目负责人手动执行 `docker compose down -v`。

## 9. 冒烟测试

冒烟测试只验证基础设施，使用专门的测试对象，不涉及任何业务表。测试脚本必须可以重复执行，每次执行之前先清理上一次留下的测试对象。

### 9.1 离线冒烟测试

1. 在 `gateway` 容器中以 cluster 模式向 YARN 提交一个 Spark SQL 作业。
2. 该作业创建数据库 `dp_smoke` 和表 `dp_smoke.t_offline`，写入 3 行数据。
3. 通过 HiveServer2 的 JDBC 接口查询 `dp_smoke.t_offline` 的行数。
4. 行数等于 3 时测试通过。

这项测试同时验证了四件事：Spark 能够向 YARN 提交作业，Spark 能够访问 Hive 3.1.3 的 Metastore，数据能够写入 HDFS，以及 Spark 与 Hive 看到的是同一套元数据。

### 9.2 实时冒烟测试

1. 在 Kafka 中创建主题 `dp_smoke_rt`，在 ClickHouse 中创建表 `dp.smoke_rt`。
2. 向 Flink 集群提交一个 Flink SQL 作业，该作业把 `dp_smoke_rt` 主题中的 JSON 消息写入 `dp.smoke_rt` 表。
3. 向主题写入 3 条消息。
4. 在 60 秒之内查询到 `dp.smoke_rt` 表的行数等于 3 时测试通过。
5. 测试结束之后取消该 Flink 作业。

Flink 写入 ClickHouse 所用的连接器待验证：优先使用 Flink 的 JDBC 连接器配合 ClickHouse 的 JDBC 驱动。如果该组合在 Flink 1.20 上不可用，实现者应当在合并请求中说明，并提出备选方案由架构师决定。

## 10. 已知风险

| 风险 | 影响 | 验证的任务卡 |
| --- | --- | --- |
| Hive 3.1.3 与 Hadoop 3.3.6 存在 Guava 之外的其他依赖冲突。 | Hive 服务无法启动。 | M0-01 |
| Spark 3.5 按照第 7.4 节配置之后仍然无法访问 Hive 3.1.3 的 Metastore。 | 离线链路的版本基线需要调整。 | M0-02 |
| Flink 1.20 的 JDBC 连接器不支持 ClickHouse。 | 实时链路写入服务层的方式需要调整。 | M0-03 |
| DolphinScheduler 3.4.2 官方镜像中的 JDK 版本高于 8，与 Hadoop 3.3.6 的客户端不兼容。 | 调度节点提交作业的方式需要调整。 | M0-04 |
| DataHub 1.7.0 复用 KRaft 模式的 Kafka 3.9 时存在兼容性问题。 | 治理组需要单独部署 Kafka。 | M0-05 |
| 服务器无法访问 Docker Hub 或 Apache 官方归档站点。 | 镜像无法拉取或构建。 | M0-01，通过 `.env` 中的镜像地址与下载地址变量解决 |

上述任何一项风险成为事实时，实现者应当停止受影响的部分，并且按照 `docs/08-开发规范与任务拆解.md` 第 8 节的设计变更流程处理。
