# 00 制造业数据中台总体架构设计（整车制造场景）

> 文档状态：已确认（2026-11-15 修订：全工程改用 JDK 8，后端改用 Spring Boot 2.7，确定多 agent 协作模式）。本文档是全部详细设计文档的上位文档，coding agent 在实现任何里程碑之前都应当先阅读本文档。
> 在线版本（含架构图）：https://claude.ai/artifact/D72XnXQPt96Ur58YdVHugZ

## 1. 文档说明与结论摘要

本文档用于确定数据中台的总体架构，只做架构层面的决策，不包含表结构、接口定义和代码。表结构、接口与任务清单由编号 01 至 08 的详细设计文档给出。

已经确认的决策如下：

- 业务场景为制造业的数字化改造，具体对象为传统整车制造企业。
- 技术路线采用经典 Hadoop 体系，即 HDFS、Hive、Spark、Flink、Kafka、ClickHouse 与 DolphinScheduler。
- 数据治理以集成开源治理组件为主，选定 DataHub 作为元数据与治理中心。
- 测试环境部署在阿里云服务器上，以 Docker Compose 编排全部组件。
- 版本基线为 Hive 3.1.3 配合 Spark 3.5，全工程统一使用 JDK 8，Web 平台后端使用 Spring Boot 2.7。
- 数据质量的执行引擎采用 Maven 工程内的轻量 Spark 规则执行模块。
- 制造驾驶舱在 Web 平台内使用 ECharts 自行研发。
- 全部设计文档以 Git 仓库的 `docs/` 目录为唯一事实来源，“数仓开发”项目中的文档只作为镜像。
- 项目采用多 agent 协作模式：Claude 担任架构师，负责整体设计与审查；Codex 负责具体开发。协作规则见第 12 节。
- 阿里云服务器的规格为 8 核 CPU、32 GB 内存，操作系统为 Ubuntu 22.04。

本文档的核心结论有三条：

1. 架构采用离线与实时并行的 Lambda 结构。离线链路由 Spark SQL 在 Hive 上完成分层建模，实时链路由 Flink 在 Kafka 上完成分层加工，两条链路的结果统一写入 ClickHouse 对外服务。
2. 数据治理不是事后补做的模块，而是嵌入到建模、开发、调度三个环节：建模之前进行命名与标准校验，任务运行时自动上报血缘，任务结束后执行质量规则。
3. DolphinScheduler 自 3.3.0 版本起已经移除内置的数据质量模块，DataHub 的开源版本只展示质量结果而不执行规则，因此质量规则的执行由本工程的 `dp-quality` 模块承担。

## 3. 业务场景与范围假设

原型以一家传统整车制造企业的单个工厂为对象，覆盖冲压、焊装、涂装、总装四大工艺车间的生产制造过程。选择车企的理由是其离散制造过程同时具备业务系统数据与设备时序数据，能够自然地同时体现离线数仓与实时数仓。

传统制造企业的数据治理痛点决定了本项目的治理重点，主要有以下三类：

- 各业务系统独立建设，物料、设备、车型、供应商等主数据在不同系统中编码不一致。
- 同一个指标在不同部门的口径不一致，例如“合格率”在车间与质量部门的计算方式不同。
- 设备数据采集频率高、数据量大，但缺少质量监控，缺失与异常值难以及时发现。

原型的数据源全部由模拟程序生成，分为以下四类：

| 来源系统 | 典型数据 | 载体 | 采集方式 |
| --- | --- | --- | --- |
| 制造执行系统（MES） | 生产工单、工序报工、车辆过点记录 | MySQL | 离线批量抽取，同时实时变更捕获 |
| 质量管理系统（QMS） | 质检记录、缺陷记录、返修记录 | MySQL | 离线批量抽取，同时实时变更捕获 |
| 企业资源计划系统（ERP） | 物料主数据、供应商、库存流水 | MySQL | 离线批量抽取 |
| 设备物联网采集 | 设备状态、传感器遥测、停机事件 | Kafka | 实时消费，并落地到 HDFS 供离线使用 |

原型的范围边界为生产、质量、设备、物料四个主题域。销售、售后、财务等主题域不在原型范围之内，但分层与命名规范为其预留了扩展位置。

## 4. 总体架构

数据自下而上流经数据源、采集层、数仓层、服务层、应用层五个层次，数据治理作为纵向能力贯穿采集层到服务层。

```
┌──────────────────────────────────────────────────────────┐ ┌──────────────────┐
│ 应用层   Web 统一门户 │ 制造驾驶舱 │ 指标管理与查询        │ │ 数据治理 DataHub │
├──────────────────────────────────────────────────────────┤ │                  │
│ 服务层   ClickHouse 服务层存储 │ 数据服务接口 Spring Boot │ │ 元数据目录       │
├──────────────────────────────────────────────────────────┤ │ 数据血缘         │
│ 数仓层   离线数仓 Hive + Spark SQL                        │ │ 数据标准与术语   │
│            ODS → DWD / DIM → DWS → ADS                   │ │ 质量规则与结果   │
│          实时数仓 Kafka + Flink                           │ │ 安全分级标签     │
│            ODS → DWD → DWS                               │ │                  │
├──────────────────────────────────────────────────────────┤ │ 建模之前：校验规范│
│ 采集层   Spark JDBC 批量抽取 │ Flink CDC │ Kafka 消息接入 │ │ 运行之中：上报血缘│
├──────────────────────────────────────────────────────────┤ │ 运行之后：执行质检│
│ 数据源   MES │ QMS │ ERP │ 设备物联网（均为模拟生成）     │ │                  │
└──────────────────────────────────────────────────────────┘ └──────────────────┘
  基础设施：HDFS · YARN · DolphinScheduler 调度 · Docker Compose
```

| 层次 | 职责 | 承载组件 |
| --- | --- | --- |
| 数据源 | 模拟程序持续生成业务系统数据和设备遥测数据。 | MySQL、Kafka |
| 采集层 | 离线链路每日批量抽取业务库，实时链路捕获业务库变更并接入设备消息。 | Spark、Flink CDC、Kafka |
| 数仓层 | 按照统一的分层与维度建模规范加工数据，离线与实时共用一套维度和指标定义。 | Hive、Spark SQL、Flink、Kafka |
| 服务层 | 存放面向查询的结果数据，并以统一接口对外提供指标查询。 | ClickHouse、Spring Boot |
| 应用层 | 提供平台的统一入口、指标管理和制造驾驶舱。 | Vue 3、ECharts |
| 数据治理 | 汇集各层元数据与血缘，管理数据标准，展示质量结果与安全分级。 | DataHub、质量规则模块 |
| 基础设施 | 提供存储、资源管理与任务调度。 | HDFS、YARN、DolphinScheduler |

## 5. 技术选型与版本基线

版本基线以“Hive 3.1.3 配合 Spark 3.5、Flink 使用 1.20 长期维护线、全工程统一使用 JDK 8”为原则，这一组合与国内企业的存量环境最为接近。下表中的版本是 2026 年 11 月查询到的发布情况，组件之间的实际兼容性需要在里程碑 M0 中逐项验证。

| 类别 | 组件 | 版本基线 | 选型理由 |
| --- | --- | --- | --- |
| 运行时 | JDK、Maven | JDK 8、Maven 3.6.3 及以上 | Hadoop 3.3.6 只支持在 Java 8 或 Java 11 上运行，Hive 3.1.3 只支持 Java 8，而 Spark 作业提交到 YARN 之后运行在 Hadoop 的容器环境中，因此全工程统一使用 JDK 8，只维护一套编译环境。 |
| 存储与资源 | Hadoop（HDFS、YARN） | 3.3.6 | Spark 3.5 的预编译发行包基于 Hadoop 3.3 版本线，两者的客户端版本保持一致。 |
| 数仓元数据与查询 | Hive（Metastore、HiveServer2） | 3.1.3 | 该版本在国内企业的存量环境中使用最广。Hive 只承担元数据与交互查询，不承担 ETL 计算。 |
| 离线计算 | Spark（运行在 YARN 上，Scala 2.12） | 3.5.x | 该版本线成熟稳定。连接 Hive 3.1.3 的 Metastore 时需要显式配置 Metastore 版本与对应的客户端依赖包。 |
| 实时计算 | Flink | 1.20.x | 1.20 线是 1.x 系列的长期维护版本，仍在持续发布修复版本，连接器生态比 2.x 线更成熟。该版本可以运行在 Java 8 上，但是 Java 8 已被标记为废弃，运行时会出现一条警告日志。 |
| 变更捕获 | Flink CDC | 3.6.0 | 该版本同时提供面向 Flink 1.20 与 2.2 的发行包。 |
| 消息队列 | Kafka（KRaft 模式） | 3.9.x | KRaft 模式不再依赖 ZooKeeper，可以减少一个容器。业务数据与 DataHub 共用同一个集群。 |
| 分析型数据库 | ClickHouse | 当前长期支持版本 | 承担服务层的高并发聚合查询，岗位要求中明确列出。 |
| 任务调度 | DolphinScheduler | 3.4.2 | 提供可视化工作流编排，支持依赖触发与补数据。 |
| 数据治理 | DataHub | 1.7.0 | 社区活跃，覆盖元数据、血缘、术语表与数据域，并且支持 Spark 与 Flink 的血缘采集。 |
| 平台数据库 | MySQL | 8.0.x | 同时作为模拟业务库、Hive Metastore 库、调度库与平台库，按数据库名隔离。 |
| Web 平台 | Spring Boot、Vue | 2.7.x、3.x | 后端与数仓模块同属 Java 与 Maven 体系。Spring Boot 3 要求 JDK 17，为了保持全工程统一使用 JDK 8，后端选用 Spring Boot 2.7。 |

选型中有三处取舍需要说明：

- 没有选择 Apache Atlas。Atlas 与 Hive 的集成最为原生，但它额外依赖 HBase 与 Solr，内存占用更高，版本更新也明显慢于 DataHub。
- 没有选择 Flink 2.x。原型更看重连接器的稳定性，升级到 2.x 可以作为后续迭代项。
- 离线 ETL 统一使用 Spark SQL，而不使用 Hive 自身的执行引擎。这样可以少部署 Tez，并且让血缘采集只需要对接 Spark 一种引擎。

已知风险有两处，都安排在里程碑 M0 中验证。第一处是 Hive 3.1.3 自带的 Guava 依赖包版本低于 Hadoop 3.3 所需的版本，构建镜像时需要替换该依赖包。第二处是 Spark 3.5 内置的 Hive 客户端版本为 2.3.9，访问 Hive 3.1.3 的 Metastore 时需要显式配置 `spark.sql.hive.metastore.version` 与 `spark.sql.hive.metastore.jars`。

## 6. 数据仓库设计概要

数据仓库采用五层结构和维度建模方法，离线与实时两条链路共用同一套分层、维度和指标定义。

### 6.1 分层标准

| 层次 | 名称 | 职责 | 离线载体 | 实时载体 |
| --- | --- | --- | --- | --- |
| ODS | 贴源层 | 保持与源系统一致的结构，只做分区与格式转换。 | Hive | Kafka |
| DWD | 明细层 | 按业务过程组织事实表，完成清洗、编码统一与维度关联。 | Hive | Kafka |
| DIM | 维度层 | 存放一致性维度，同时承担主数据编码映射。 | Hive | MySQL 维表 |
| DWS | 汇总层 | 按主题域和统计周期汇总公共指标。 | Hive | ClickHouse |
| ADS | 应用层 | 面向驾驶舱与接口的结果表。 | Hive，并导出到 ClickHouse | ClickHouse |

### 6.2 主题域与总线矩阵

原型划分生产、质量、设备、物料四个主题域。下表是业务过程与一致性维度的总线矩阵，“是”表示该业务过程的事实表关联该维度。

| 主题域 | 业务过程 | 日期 | 组织（工厂、车间、产线、工位） | 班次 | 车型 | 设备 | 物料 | 供应商 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 生产 | 工序报工 | 是 | 是 | 是 | 是 | 是 | | |
| 生产 | 车辆过点 | 是 | 是 | 是 | 是 | | | |
| 质量 | 质量检验 | 是 | 是 | 是 | 是 | | | |
| 质量 | 缺陷记录 | 是 | 是 | 是 | 是 | | 是 | 是 |
| 设备 | 设备停机 | 是 | 是 | 是 | | 是 | | |
| 设备 | 设备遥测 | 是 | 是 | | | 是 | | |
| 物料 | 库存出入库 | 是 | 是 | | | | 是 | 是 |

### 6.3 命名规范

表名统一采用“层次_主题域或来源_业务含义_更新方式或统计周期”的格式，全部使用小写字母与下划线。

| 层次 | 示例表名 | 含义 |
| --- | --- | --- |
| ODS | `ods_mes_work_order_df` | 来自 MES 的生产工单，每日全量。 |
| DWD | `dwd_prod_work_report_di` | 生产域工序报工明细，每日增量。 |
| DIM | `dim_equipment_df` | 设备维度，每日全量。 |
| DWS | `dws_equip_line_runtime_1d` | 设备域按产线汇总的运行时长，统计周期为一天。 |
| ADS | `ads_equip_oee_1d` | 设备综合效率日报。 |

指标命名遵循“派生指标等于日期周期、修饰词与原子指标的组合”的规则。例如“最近 7 天总装车间一次合格率”由日期周期“最近 7 天”、修饰词“总装车间”和原子指标“一次合格率”组成。

### 6.4 核心指标

原型围绕八个制造业通用指标建设：产量、计划达成率、一次合格率、单车缺陷数、设备综合效率、平均故障间隔时间、平均修复时间和库存周转天数。其中设备综合效率（OEE）等于时间开动率、性能开动率与合格品率三者的乘积，它同时依赖设备、生产、质量三个主题域，是检验跨域建模是否正确的核心用例。

### 6.5 两条加工链路

离线链路每日凌晨执行一次，步骤如下：

1. Spark 作业通过 JDBC 抽取 MySQL 业务表，写入 Hive 的 ODS 分区。
2. Spark SQL 作业依次加工 DIM、DWD、DWS、ADS 各层。
3. 每一层加工完成后执行该层的质量规则，强规则失败时阻断下游任务。
4. Spark 作业将 ADS 结果导出到 ClickHouse。
5. 以上步骤由 DolphinScheduler 的一个工作流按依赖关系编排。

实时链路持续运行，步骤如下：

1. Flink CDC 捕获 MES 与 QMS 的变更并写入 Kafka 的 ODS 主题，设备遥测直接进入 Kafka。
2. Flink 作业完成清洗并关联 MySQL 维表，写入 Kafka 的 DWD 主题。
3. Flink 作业按分钟窗口汇总，将实时产量、实时设备状态和参数越限告警写入 ClickHouse。

实时结果用于当日监控，次日由离线结果覆盖修正，这是 Lambda 结构保证最终准确性的方式。

## 7. 数据治理设计概要

数据治理以 DataHub 为中心，按照“事前制定规范、事中配置开发、事后系统检测”的思路，把治理动作分别嵌入建模、任务运行和任务完成三个时点。原型处于数仓初始阶段，治理的重点是命名规范、指标口径、元数据与质量规则，资源治理与成本治理暂不实现。

| 治理能力 | 实现方式 | 生效时点 |
| --- | --- | --- |
| 命名与建模规范 | Web 平台的模型设计页面按第 6.3 节的规则校验表名、字段名和分层依赖，校验通过后生成建表语句。 | 建模之前 |
| 数据标准与指标口径 | DataHub 的业务术语表存放标准术语、编码标准和指标口径，并关联到具体的表与字段。 | 建模之前 |
| 主数据 | DIM 层建立设备、物料、车型、组织的统一编码，并维护各源系统编码到统一编码的映射表。 | 建模之前 |
| 元数据采集 | DataHub 的采集任务定时扫描 Hive Metastore、Kafka、ClickHouse 与 MySQL。 | 每日定时 |
| 数据血缘 | Spark 作业挂载 DataHub 的 Spark 代理自动上报表级与字段级血缘，Flink 作业的血缘通过 DataHub 的 Flink 集成采集。 | 运行之中 |
| 数据质量 | `dp-quality` 模块在每层加工完成后执行规则，结果上报到 DataHub 并显示在对应数据表的页面上。 | 运行之后 |
| 数据安全 | DataHub 的标签标记公开、内部、敏感三个级别，数据服务接口根据标签对敏感字段脱敏。 | 查询之时 |
| 数据资产 | DataHub 的数据域对应四个主题域，每张表登记负责人。 | 持续维护 |

### 7.1 数据质量的实现方案

数据质量的执行引擎采用已经确认的方案：在 Maven 工程中编写一个基于 Spark SQL 的轻量规则执行模块，结果通过 DataHub 接口上报。该方案与整体 Java 技术栈一致，不增加容器，可以由调度直接编排并阻断下游。被放弃的备选方案是引入 Great Expectations，放弃的原因是它会引入 Python 技术栈并与 Maven 工程分离。

规则覆盖完整性、唯一性、有效性、及时性、一致性和波动性六个维度，并区分强规则与弱规则：强规则失败时阻断下游任务，弱规则失败时只告警。

## 8. Web 平台设计概要

Web 平台是数据平台的统一入口，它只实现 DataHub 与 DolphinScheduler 不具备的能力，已有能力通过跳转或接口调用的方式集成，不重复建设。后端采用 Spring Boot 2.7，前端采用 Vue 3、Element Plus 与 ECharts。

| 功能模块 | 主要功能 | 实现方式 |
| --- | --- | --- |
| 门户首页 | 展示资产数量、任务运行情况和质量得分概览。 | 自行研发，调用各组件接口 |
| 模型设计 | 录入表的分层、主题域和字段，校验命名规范，生成建表语句。 | 自行研发 |
| 指标管理 | 管理原子指标、修饰词、日期周期和派生指标，绑定指标到数据模型。 | 自行研发 |
| 质量管理 | 配置质量规则，查看每次执行的结果与趋势。 | 自行研发，结果同步到 DataHub |
| 数据服务 | 按指标名称、维度和时间范围查询 ClickHouse 的统一接口。 | 自行研发 |
| 制造驾驶舱 | 展示产量、合格率、设备综合效率的离线报表与实时监控。 | 自行研发（ECharts） |
| 数据地图与血缘 | 检索数据表，查看字段、负责人和上下游血缘。 | 跳转到 DataHub |

用户与权限在原型阶段只实现登录和两种角色，即数据开发人员与业务分析人员。

## 9. Maven 工程结构

工程采用一个父工程加六个子模块的结构，模块按运行时引擎划分，使 Spark、Flink 与 Spring Boot 三套依赖互不干扰。包名根路径为 `com.leejean`，源码编码为 UTF-8，关键代码添加中英文双语注释，这些约定均来自项目的 CLAUDE.md。

```
dataplatform/                     父工程，统一管理依赖版本
├── pom.xml
├── .gitignore                    面向 Maven 工程的忽略规则
├── AGENTS.md                     面向 Codex 的项目指令
├── dp-common/                    公共配置、常量与工具类
├── dp-mock/                      模拟数据生成（业务库数据与设备遥测）
├── dp-warehouse-offline/         离线数仓（Spark 批量抽取、Spark SQL 运行器与各层脚本）
├── dp-warehouse-realtime/        实时数仓（Flink CDC 采集与 Flink 作业）
├── dp-quality/                   质量规则执行与结果上报
├── dp-portal-server/             Web 平台后端（Spring Boot）
├── dp-portal-web/                Web 平台前端（Vue，独立的 npm 工程）
├── deploy/                       Docker 编排、初始化脚本、DataHub 采集配置、调度工作流定义
└── docs/                         设计文档
```

模块划分有四点需要说明：

- 初稿中的 `dp-ingest` 模块已经取消。该模块同时包含 Spark 作业与 Flink 作业，违背了“按运行时引擎划分模块”的原则，因此 Spark 批量抽取并入 `dp-warehouse-offline`，Flink CDC 采集并入 `dp-warehouse-realtime`。
- 离线数仓的加工逻辑以 SQL 脚本文件的形式存放在资源目录中，Java 代码只提供一个通用的运行器。这样做符合“最少代码”的原则，也便于数据开发人员评审。
- 质量模块按照第 7.1 节已经确认的方案实现，以 Spark SQL 执行规则，并通过 DataHub 接口上报结果。
- 依赖 Spark 的模块统一使用 Scala 2.12 版本的 Spark 3.5 依赖，并将其声明为 provided 范围，由集群在运行时提供。

## 10. Docker 环境规划

测试环境部署在一台 x86 架构的阿里云 ECS 服务器上，全部组件由 Docker Compose 编排。各容器的内存上限合计约 28 GB，因此已经确认的服务器规格为 8 核 CPU、32 GB 内存和 200 GB 云盘，操作系统为 Ubuntu 22.04。下表中的内存数值是各分组的容器内存上限之和，每个容器的上限见“01 环境与部署设计”第 5 节，实际占用需要在里程碑 M0 中实测。

| 分组 | 容器 | 内存上限合计（GB） | 用途 |
| --- | --- | --- | --- |
| 核心组 | MySQL、NameNode、DataNode、ResourceManager、NodeManager、Hive Metastore、HiveServer2、作业提交网关 | 12.5 | 离线数仓的最小运行环境 |
| 实时组 | Kafka、Flink JobManager、Flink TaskManager、ClickHouse | 6.5 | 实时数仓与服务层存储 |
| 调度组 | DolphinScheduler（单机模式） | 2 | 工作流调度 |
| 治理组 | DataHub 的元数据服务、前端、检索引擎、动作服务 | 5.5 | 元数据与治理 |
| 平台组 | 平台后端、平台前端 | 1.25 | Web 平台 |

环境规划遵循以下约定：

- 五个分组对应 Docker Compose 的五个 profile，每个分组都配有独立的启动脚本和健康检查脚本。
- DataHub 复用实时组的 Kafka 与核心组的 MySQL，不再单独部署这两个依赖。
- 中国大陆地域的服务器直接访问 Docker Hub 可能不稳定，因此镜像统一推送到阿里云容器镜像服务的个人仓库后再拉取，Maven 依赖使用阿里云的镜像仓库。
- 原型中的 HDFS、YARN、Kafka 等组件没有启用身份认证，因此安全组不对公网开放任何组件端口。各组件的管理页面和 Web 平台通过 SSH 隧道访问，或者只对固定的公网地址放行。
- 代码在本地的 IntelliJ IDEA 中开发并运行单元测试，由 Maven 打包后通过脚本上传到服务器提交运行。

服务器建议采用按量付费的计费方式，不使用时停机。

## 12. 协作模式

项目采用多 agent 协作模式，三方的职责如下：

| 角色 | 承担者 | 职责 |
| --- | --- | --- |
| 架构师 | Claude | 撰写与修订设计文档，拆解任务卡，审查合并请求。 |
| 开发者 | Codex | 按任务卡实现代码与脚本，运行验收命令，提交合并请求。 |
| 项目负责人 | 用户 | 确认设计决策，在两个 agent 之间传递任务与结果，合并代码，操作阿里云环境。 |

协作遵循以下规则：

1. Git 仓库是唯一事实来源。设计文档位于 `docs/` 目录，面向 Codex 的项目指令位于仓库根目录的 `AGENTS.md`。
2. 开发任务以任务卡的形式下达，任务卡位于 `docs/tasks/` 目录。每张任务卡包含目标、依据的设计文档章节、明确不做的范围、验收命令和交付物。
3. 一张任务卡对应一个分支和一个合并请求。合并请求的描述中必须附上验收命令的实际输出。
4. Codex 发现设计存在问题时不得自行修改设计，应当在合并请求或任务卡中提出，由架构师修订文档之后再继续。
5. 架构师对照设计文档审查代码差异与验收证据，审查通过之后由项目负责人合并。
